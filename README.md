# Alfred Flight Monitor

Открытый репозиторий: [github.com/vanya-kirs/alfred-flight-monitor](https://github.com/vanya-kirs/alfred-flight-monitor)

Первый рабочий backend-срез сервиса «Альфред, друг Бэтмена». Он регистрирует рейсы, принимает наблюдение от заменяемого провайдера, отсеивает устаревшие данные и создаёт внутрисистемное уведомление при задержке или отмене.

Сервис не перебронирует рейсы без подтверждения владельца поездки. PAN/CVV и паспортные поля не хранятся: принимаются только непрозрачные токены внешнего платёжного/документного хранилища.

## Что уже работает

- регистрация и просмотр рейсов;
- timezone-aware время с нормализацией в UTC;
- проверка статуса через интерфейс провайдера;
- защита от запоздавших наблюдений;
- уведомления о задержке и отмене без дублей;
- простой веб-интерфейс с кнопками для добавления и проверки рейсов;
- поиск билетов в одну сторону и туда-обратно по городам, датам и числу пассажиров;
- поиск по тысячам IATA-аэропортов и названиям городов через локальную базу `airportsdata`;
- не менее 12 сравнимых демонстрационных вариантов на маршрут;
- сравнение цены, длительности, пересадок, багажа и транзитных визовых рисков;
- автоматические плюсы/минусы и сортировка по рекомендации, цене, скорости или пересадкам;
- сохранение выбранного варианта в план поездки без покупки и бронирования;
- переход на реальную выдачу Aviasales для покупки у агентства или авиакомпании;
- OpenAPI/Swagger на `/docs`;
- групповые multi-city поездки с ролями owner/editor/viewer, приглашениями и аудитом;
- единый timezone-aware маршрут, поиск пересечений и версия плана для офлайн-синхронизации;
- персональный inbox с идемпотентной доставкой для офлайн-пользователей;
- инциденты задержки/отмены, автоматический поиск альтернатив и owner-approved замена рейса;
- демо-каталоги отелей, трансферов и активностей с плюсами, минусами и checkout-ссылкой;
- состояние бронирования и добавление подтверждённой услуги в общий план;
- предпочтения/feedback и объяснимое ранжирование активностей;
- ссылки на паспортные данные с удалением через 24 часа после поездки или через 30 минут для брошенного оформления;
- детерминированный demo-провайдер для разработки без внешнего API-ключа.
- локальные аккаунты с регистрацией, подтверждением пароля, входом и выходом;
- хранение паролей только в виде `scrypt`-хеша с индивидуальной солью;
- поиск отелей с фильтрами удобств, питания и расположения;
- предварительный план на каждый день и раздел «Мои бронирования» с расчётом стоимости.

Аккаунты сохраняются локально в `data/accounts.sqlite3`; каталог `data/` исключён из Git и не публикуется. Остальные демонстрационные данные поездки пока находятся в памяти или браузерном хранилище. Цены и наличие мест внутри карточек демонстрационные. Прямого билетного API сейчас нет: кнопка покупки формирует маршрутный URL Aviasales и открывает реальную выдачу. Для реальных цен внутри приложения нужен токен Travelpayouts Data API; realtime Flight Search API Travelpayouts требует отдельного одобрения проекта и 50 000 MAU.

## Запуск

```bash
python3 -m venv .venv
.venv/bin/pip install -e '.[dev]'
.venv/bin/uvicorn alfred_flights.main:app --reload
```

После запуска:

- API: `http://127.0.0.1:8000`
- пользовательский интерфейс: `http://127.0.0.1:8000/`
- Swagger: `http://127.0.0.1:8000/docs`
- проверка здоровья: `http://127.0.0.1:8000/health`

## Демонстрационный сценарий

Веб-интерфейс на `/` позволяет выполнить поиск, изменить сортировку, прочитать плюсы и минусы каждого варианта и добавить один из них в план поездки.

Поиск также доступен через API:

```bash
curl -s -X POST http://127.0.0.1:8000/ticket-search \
  -H 'Content-Type: application/json' \
  -d '{"origin":"Москва","destination":"Стамбул","departure_date":"2026-12-10","adults":2,"checked_baggage_required":true,"sort_by":"recommended"}'
```

Мониторинг существующего рейса:

Создать рейс:

```bash
curl -s -X POST http://127.0.0.1:8000/flights \
  -H 'Content-Type: application/json' \
  -d '{"flight_number":"SU 100","departure_at":"2026-11-10T07:30:00Z"}'
```

Скопировать `id` из ответа и имитировать задержку данных провайдера:

```bash
curl -i -X POST http://127.0.0.1:8000/demo/flights/FLIGHT_ID/observation \
  -H 'Content-Type: application/json' \
  -d '{"state":"delayed","observed_at":"2026-11-10T04:00:00Z","delay_minutes":75}'
```

Запустить проверку и прочитать уведомления:

```bash
curl -s -X POST http://127.0.0.1:8000/flights/FLIGHT_ID/check
curl -s http://127.0.0.1:8000/notifications
```

## Структура

```text
src/alfred_flights/
├── domain.py           # сущности и правила актуальности статусов
├── application.py      # сценарии регистрации и мониторинга
├── api.py              # FastAPI-контракт и перевод ошибок
├── main.py             # точка запуска
├── adapters/memory.py  # временные репозитории и demo-провайдер
└── ticket_search/      # поиск, оценка, сортировка и demo-каталог билетов
```

Архитектурные решения описаны в `docs/superpowers/specs/2026-11-07-flight-monitor-design.md`, план реализации — в `docs/superpowers/plans/2026-11-07-flight-monitor-mvp.md`.

## Следующий рекомендуемый срез

Подключить реального поставщика тарифов через существующий интерфейс провайдера, затем добавить PostgreSQL-репозитории, миграции и фоновый worker с Redis. После этого можно объединить события мониторинга с автоматическим запуском поиска альтернатив.
